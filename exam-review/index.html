Week 10

Caching and Efficient Model Integration

ปัญหา: Rerun ทำงานซ้ำ

Streamlit รันไฟล์ Python ใหม่ตั้งแต่บนลงล่างทุกครั้งที่ผู้ใช้กด widget หรือแก้ source code งานช้าอย่าง load_model() จึงถูกรันซ้ำทุกรอบ แม้โมเดลไม่ได้เปลี่ยน

งานที่ควร cache: อ่านไฟล์ใหญ่ (CSV/Excel/JSON), เรียก API/database, เตรียม AI tools (model, tokenizer, embeddings)

Cache งานที่ แพง และ คงที่พอ จะใช้ซ้ำข้าม rerun ได้

Cache hit / Cache miss

CACHE HIT
มี entry ที่ตรงกัน → คืนค่าที่เก็บไว้ ตัวฟังก์ชัน ไม่ถูกรัน
CACHE MISS
ไม่มี entry → รันฟังก์ชัน แล้วเก็บผลลัพธ์ไว้
@st.cache_data
def slow_square(x):
    time.sleep(3)
    return x * x

slow_square(5)  # MISS → คำนวณ 25 แล้วเก็บ
slow_square(5)  # HIT
slow_square(7)  # MISS → คำนวณ 49 แล้วเก็บ
slow_square(5)  # HIT

ฟังก์ชันเดียวเก็บได้ หลาย entry แยกตาม cache identity

Cache ข้ามแค่ ตัวฟังก์ชัน ที่ cache ไว้ ไม่ได้ข้ามการ rerun ส่วนอื่นของสคริปต์ยังรันใหม่ทั้งหมด

Cache identity: เมื่อไรจะ hit

  1. เป็นฟังก์ชันที่ decorate ตัวเดิม
  2. argument ตรงกับที่เคยเรียก (ยกเว้น parameter ที่ตั้งใจละไว้)
  3. source code ของฟังก์ชันไม่ถูกแก้

ข้อใดข้อหนึ่งเปลี่ยน → cache miss → สร้าง entry ใหม่

cache_data vs cache_resource

@st.cache_data@st.cache_resource
ใช้กับDataFrame, array, dict, list, str, ตัวเลข, ผลจาก APIML model, DB connection, engine, handle ที่ใช้ร่วมกัน
ผู้เรียกได้สำเนา ของตัวเอง (serialize/deserialize)object ตัวเดียวกัน ไม่มีการ copy
แก้ไข objectไม่กระทบคนอื่นทุก session เห็นการแก้ไข
ข้อควรระวังข้อมูลอาจเก่า (stale)ต้อง thread-safe, ห้าม mutate แบบไม่ปลอดภัย
 
@st.cache_resource
def get_numbers():
    return [1, 2, 3]

numbers = get_numbers()
numbers.remove(1)
# รอบแรก: object ที่แชร์กลายเป็น [2, 3]
# rerun ถัดไป: ได้ object เดิม [2, 3] → remove(1)
# ValueError: 1 is not in list

คำถามที่ใช้ตัดสิน: ผู้เรียกควรได้ผลลัพธ์ที่แยกกัน หรือตั้งใจใช้ object เดียวร่วมกัน?

Hashing และ underscore

@st.cache_data
def fetch_data(_db_connection, num_rows):
    return _db_connection.fetch(num_rows)
# _db_connection ไม่นับเป็น cache key
# num_rows นับเป็น cache key

parameter ต้อง hashable เพื่อใช้เป็น key ถ้า hash ไม่ได้ให้ใส่ _ นำหน้า แต่ อย่าละ parameter ที่มีผลต่อผลลัพธ์

Advanced: ความสดของข้อมูลและหน่วยความจำ

  • ttl=3600 หรือ ttl=datetime.timedelta(hours=1) → entry หมดอายุแล้วรันใหม่ (แก้ปัญหาข้อมูลเก่า)
  • max_entries=1000 → จำกัด จำนวน entry เมื่อเต็มจะลบอันเก่าสุดออก (ไม่ได้คุมขนาดเป็นไบต์)
  • show_spinner=False สำหรับงานเร็ว หรือ show_spinner="Fetching data..." เพื่อบอกผู้ใช้ตอน miss
  • load_data.clear() ล้างเฉพาะฟังก์ชันนั้น, st.cache_data.clear() / st.cache_resource.clear() ล้างทั้งประเภท
@st.cache_data
def load_data(path, file_mtime):
    return pd.read_csv(path)

mtime = os.path.getmtime("data.csv")
df = load_data("data.csv", mtime)  # ไฟล์เปลี่ยน → mtime เปลี่ยน → miss
ถ้าแหล่งข้อมูลจริงเปลี่ยน ให้ทำให้การเปลี่ยนนั้นปรากฏใน input ของฟังก์ชัน

ควร cache หรือไม่

ควร
อ่านไฟล์/DB/API ที่แพง (มีกฎความสด) · transformation ที่แพงและ input ซ้ำ · โหลดโมเดลที่ใช้ซ้ำ
อาจจะ: prediction ที่ request ซ้ำกันจริง
ไม่ควร
เลขคณิตง่ายๆ · input ไม่ซ้ำแทบทุกครั้ง · state ของผู้ใช้ที่เปลี่ยนได้ · งานที่มี side effect ต้องเกิดทุกครั้ง

ถามสองข้อ: ใช้ซ้ำแล้วประหยัดจริงไหม? ใช้ซ้ำแล้วยังถูกต้องไหม?

Week 11

Session State and Stateful Interaction

Session คืออะไร

1 แท็บเบราว์เซอร์ = 1 session คือการเชื่อมต่อหนึ่งครั้งระหว่างแท็บกับแอป server และแอปใช้ร่วมกัน แต่ st.session_state ของแต่ละ session แยกกัน เปิดแท็บใหม่ = state ใหม่

Session StateCache
Scopeหนึ่ง browser sessionใช้ร่วมกันทุก session บน app/server เดียวกัน
จุดประสงค์จำค่าของผู้ใช้ที่เปลี่ยนไปเรื่อยๆใช้ผลงานที่แพงและคงที่ซ้ำ
อายุหายเมื่อ session จบหรือถูก resetอยู่จนถูกล้าง หมดอายุ หรือ invalidate

ใช้กับ: ประวัติแชท, ขั้นตอนของ workflow, ตัวเลือก/filter/draft ชั่วคราว

ตัวแปรธรรมดาถูกรีเซ็ตทุก rerun

# ไม่มี session state
count = 0
if st.button("Add 1"):
    count += 1
st.write("Count:", count)
# กดกี่ครั้งก็แสดง 1
# มี session state
if "count" not in st.session_state:
    st.session_state.count = 0
if st.button("Add 1"):
    st.session_state.count += 1
st.write("Count =", st.session_state.count)
Initialize ครั้งเดียว ด้วย if "key" not in st.session_state แล้วอ่าน/แก้ผ่าน st.session_state

ใช้เหมือน dictionary

st.session_state["count"] = 0      # dictionary syntax
st.session_state.count = 0         # attribute syntax
st.session_state["count"] += 1     # update
del st.session_state["count"]      # delete
for key in list(st.session_state.keys()):
    del st.session_state[key]      # ล้างทุก key

dictionary syntax อ่านง่ายกว่าเวลาวนลูป ลบ หรือตรวจ key

Widget key

st.text_input("Your name", key="name")
st.slider("Level", 1, 10, key="level")
st.write(st.session_state["name"])   # ค่าเดียวกับ widget

ใส่ key แล้วค่าของ widget จะถูกเขียนลง Session State อัตโนมัติ ต้องตั้งค่าเริ่มต้นใน state ก่อน สร้าง widget

if "celsius" not in st.session_state:
    st.session_state.celsius = 50.0
st.slider("Temperature", min_value=-100.0, max_value=100.0, key="celsius")

Callbacks

ผู้ใช้เปลี่ยน widget → callback รัน → state ถูกอัปเดต → สคริปต์ rerun

def increment_counter():
    st.session_state.count += 1

st.button("Increment", on_click=increment_counter)    # ✓ ส่งฟังก์ชัน
st.button("Increment", on_click=increment_counter())  # ✗ เรียกทันทีทุก rerun
  • on_click สำหรับปุ่ม, on_change สำหรับ text_input, slider, selectbox, checkbox
  • ส่งค่าคงที่ด้วย args / kwargs และอ่านค่า widget ใน callback ผ่าน st.session_state
  • ใน st.form callback ต้องอยู่ที่ st.form_submit_button(..., on_click=...)

Error ที่พบบ่อย

  1. อ่าน key ก่อนสร้าง → exception ให้ initialize ก่อน
  2. แก้ state หลังสร้าง widget → StreamlitAPIException: ... cannot be modified after the widget with key ... is instantiated
  3. ตั้งค่าเริ่มต้นซ้อนสองที่ (state = 7 และ value=5) → warning ให้เลือกแหล่งเดียว
  4. ตั้งค่า state ของ button → error เพราะ button เป็น True แค่ rerun เดียว ให้เก็บ ผลลัพธ์ แทน
if "submitted" not in st.session_state:
    st.session_state.submitted = False
if st.button("Submit"):
    st.session_state.submitted = True   # เก็บผลลัพธ์ ไม่ใช่สถานะปุ่ม

อายุของ session และการใช้คู่กับ cache

  • แท็บเดิม interaction ปกติ → state อยู่ต่อ
  • แท็บใหม่/ผู้ใช้ใหม่ → session ใหม่ state ใหม่
  • Reload/connection reset → state อาจหายเพราะ WebSocket เปลี่ยน
@st.cache_resource
def load_model():
    return create_model()        # ใช้ร่วมกันทุกคน

if "messages" not in st.session_state:
    st.session_state.messages = []   # แยกต่อ session
Session State คือหน่วยความจำชั่วคราวต่อ session ไม่ใช่ database ใครควรเห็น? อยู่ได้นานแค่ไหน?

Lab 12

Connecting to Database (Supabase)

Supabase คืออะไร

แพลตฟอร์ม Backend-as-a-Service (BaaS) แบบ open-source ที่สร้างบน PostgreSQL ช่วยให้สร้าง backend ได้เร็วโดยไม่ต้องเขียนโครงสร้างพื้นฐานเอง

ข้อดี

  • Relational: PostgreSQL เต็มรูปแบบ รองรับข้อมูลที่สัมพันธ์ซับซ้อน (SQL) ยืดหยุ่นกว่า NoSQL
  • ลดเวลาเขียน API: สร้าง REST และ GraphQL API ให้อัตโนมัติตาม Database Schema
  • ไม่มี Vendor Lock-in: open-source, self-host หรือย้าย cloud ได้
  • Row-Level Security (RLS) ของ PostgreSQL ควบคุมสิทธิ์ละเอียด
  • รองรับ AI: ส่วนขยาย pgvector เก็บ/ค้นหา vector สำหรับ RAG

ฟีเจอร์หลัก

Database (PostgreSQL)Authentication (อีเมล/รหัสผ่าน, OAuth: Google, GitHub)StorageRealtime (WebSockets)Edge Functions (Serverless)

สร้างโปรเจคและตาราง

  • Project: lab12_database_connection, Region: Singapore (ใกล้ที่สุด), เปิด Enable Data API
  • ตาราง helpdesk_tickets จาก helpdesk_tickets_timestamped.csv: ticket_id = Primary key, created_at = timestamp
  • ตาราง helpdesk_validation จาก helpdesk_validation_queries.csv: query_id = Primary key

Row-Level Security (RLS)

กลไกของ PostgreSQL ควบคุมสิทธิ์ ระดับแถว (row) ผ่าน Policy ว่าผู้ใช้แต่ละประเภททำ SELECT, INSERT, UPDATE, DELETE แถวไหนได้ เช่น ให้ผู้ใช้เห็นเฉพาะข้อมูลตัวเอง หรือให้แอดมินเห็นทั้งหมด

ใน Lab ปิด RLS เพราะยังไม่ใช้ Authentication และเป็นข้อมูลจำลอง เพื่อโฟกัสที่การเชื่อมต่อและ query
ระบบจริงที่มีผู้ใช้หลายประเภท ควรเปิด RLS และกำหนด Policy ให้เหมาะสม

เชื่อม Streamlit กับ Supabase

ใช้: Publishable key
sb_publishable_...
ห้ามใช้: Secret key / Service Role key
sb_secret_... มีสิทธิ์สูง ข้าม RLS ได้

เก็บค่าไว้ใน .streamlit/secrets.toml เพื่อแยก configuration ออกจาก source code (ถ้าไม่มีไฟล์ให้สร้างเอง)

Week 13

Deploying Streamlit Applications

Deploy ต้องมีอะไรบ้าง

Code → GitHub → Streamlit Community Cloud → Public URL → ผู้ใช้จริง

ส่วนประกอบบอกอะไรตัวอย่าง
Application Codeจะรันอะไรmain.py, training.py
Dependenciesต้องติดตั้ง library อะไรrequirements.txt
Configuration / Secretsค่าของ environment นี้Supabase URL และ key
Cloud Environmentรันที่ไหนPython, CPU, memory, storage

ขั้นตอน Deploy (Example 1)

  1. เตรียมและทดสอบไฟล์ในเครื่อง
  2. Push ขึ้น GitHub repository
  3. เปิด share.streamlit.io → Create app
  4. เลือก repository, branch และ main.py (entrypoint)
  5. Advanced settings (ไม่บังคับ): Python version → Deploy
  6. เปิด URL แล้วทดสอบการใช้งาน

“It works on my machine”

Cloud สร้าง Python environment ของตัวเอง ไม่ได้คัดลอก ของเราไป จึงต้องระบุ library ที่ใช้ใน requirements.txt (วางไว้ข้าง main.py) และควร pin version ที่ทดสอบแล้วเพื่อให้สร้าง environment ซ้ำได้

ความต่างระหว่าง Local กับ Cloud

  • Python version: เลือกให้ตรงกับที่ทดสอบในเครื่อง
  • Libraries: ระบุ package และตรวจ version
  • Secrets: ใส่ค่าบน cloud แยกต่างหาก
  • File paths: ไฟล์ต้องอยู่ใน repo ห้ามใช้ path เฉพาะเครื่อง
  • CPU/memory: การ train และโมเดลใหญ่ใช้ทรัพยากรจำกัด
  • Storage: ไฟล์บน cloud ไม่รับประกันว่าคงอยู่ เก็บข้อมูลถาวรใน Supabase

Develop → Commit/Push → Deploy → Test → Fix → Push again (Cloud ดู branch ที่เลือกและอัปเดตแอปเองเมื่อ push)
